Guide the human through pignolo's setup. Speak to them in their language. Never edit any user rule file.

## How to talk

- **In plain words** first (heading e.g. "En pocas palabras"): 1 to 3 short lines, no jargon, no file paths, no counts. What it means for them and what they decide. **Technical detail** (heading e.g. "Detalle técnico": commands, paths, exact counts, rules grouped by purpose) only if the human asks or something fails.
- **Closed answers use the `AskUserQuestion` tool**: recommended option first, labelled as recommended, up to 4 questions per call. If the tool is not available, ask in plain text with the same options.
- Every count and path comes from the script's JSON, never from a hand count. Group rules by purpose.
- **Explicit yes.** Nothing is written without the human's explicit yes in their own turn. An option chosen in the selector counts as that yes only for the exact setup shown on that screen.

## Fast flow

0. **Confirm (only if you chose this skill yourself).** If the turn carries a `<command-name>` tag for this skill, the user typed the command: carry on below. Otherwise run nothing yet: read `${CLAUDE_PLUGIN_ROOT}/templates/activation-confirm.md`, section `setup`, and ask with AskUserQuestion (never plain chat text) with the recommended option first, "Configurar pignolo ahora (Recomendado)", and "No ahora". On "No ahora" end this skill and carry on with what the user was doing.

1. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/setup.js" check`. Plain: "your machine is ready" or the one or two things that matter. Warnings: git older than 2.31 (no backups); no `powershell.exe` (PowerShell commands cannot be verified); superpowers present (it overlaps with pignolo; suggest uninstalling it after trying pignolo); agent teams on (not supported); `subagentModelForce` true, or an `availableModels` list that excludes `opus` or `sonnet` (the profile will not apply: name `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` or `availableModels`).
2. Without writing anything, run `node "${CLAUDE_PLUGIN_ROOT}/scripts/setup.js" permissions --target user` and, with the Write tool, collect the rule conflicts as in step 4 of the review (compare `~/.claude/CLAUDE.md`, the project `CLAUDE.md` and `.claude/rules/*.md` with `${CLAUDE_PLUGIN_ROOT}/rules/core.md`; `conflicts --check` returns only the unresolved ones). The recommended resolution: on safety the human's rule wins; on process pignolo's wins.
3. **One screen**, in plain words: whether the machine is ready; the recommended profile (the one `check` already shows, else `balanced`; one line of cost and speed); the permissions (commands that lose work are blocked; push, merge and deleting branches ask first), for all projects; how many conflicts are pending, one line each with who wins; one line on the threat model (with `auto` or `bypassPermissions` and outside content, an isolated environment is safer). Then ONE question with three options: **Apply the recommended setup** (recommended), **Review point by point**, **Cancel**.
4. Apply: `setup.js config --profile <recommended>` (show the `notice` as in review step 2 when it is `economy`), then `setup.js permissions --target user --apply` (it backs up the file first and keeps every existing rule) and, per conflict, `conflicts --record <file>` with the resolution shown. Review: the steps below. Cancel: say nothing was written. Finish with step 6.

## Review point by point

One step per message, each ending with at most one question (with options when the answer is closed).

1. **Environment check.** As in the fast flow, step 1.
2. **Profile.** One `AskUserQuestion` with one line per profile (plain: cost and speed; recommended: `balanced`). Detail: `max` is opus almost everywhere, parallelism 3, 3 refuters on high risk; `balanced` is opus for research, reviewers and debugging and sonnet for implementers, parallelism 2; `economy` is sonnet where it is safe, parallelism 1, presentation defaults to text. Reviewers and auditors run on opus in every profile, `economy` included (author decision), because a weaker reviewer approves silently. Write it with `node "${CLAUDE_PLUGIN_ROOT}/scripts/setup.js" config --profile <profile>` (optionally `--presentation ask|artifact|text` and `--language <language>`). When the profile is `economy` (just chosen, or set per `check`), the JSON carries a `notice` with `plain` and `technical` text (measured figures, spec §7): show it verbatim, plain first; other profiles have no `notice`.
3. **Permissions.** Run `setup.js permissions --target user` (and with `--target project` if they want it there); nothing is written yet. Ask with options: for all projects (recommended), only this one, or none. Detail: `add.deny.length`, `add.ask.length`, `already`, the paths, rules by purpose and side effects (the broad MCP `ask` rules). Only after an explicit yes from the human, in their own turn, run the same command with `--apply`.
4. **Rule conflicts.** Read `~/.claude/CLAUDE.md`, the project `CLAUDE.md` and `.claude/rules/*.md`, compare with `${CLAUDE_PLUGIN_ROOT}/rules/core.md`. Write one entry per conflict with the Write tool to a temporary JSON file: `[{ "source": { "path", "quote" }, "pignolo": { "rule": 1-6, "quote" }, "resolution": "human"|"pignolo"|"custom", "note"?, "project"? }]` (`project` = the project root for conflicts from a project file). Run `setup.js conflicts --check <file>`: it returns as `pending` only the unresolved ones (or whose text changed). Ask about each pending one, one per message: plain "what changes for you" and who wins; options: the recommended winner, the other side, custom. After each answer write the resolved entry (the human's own words in `note` when `custom`) to a file and run `setup.js conflicts --record <file>`. Nothing is asked twice.
5. **Threat model.** Plain: with `auto` or `bypassPermissions` and outside content (web pages, third-party issues or repos), an isolated environment is safer. Detail: WSL2 with `/sandbox`, or a devcontainer.
6. **Summary.** Plain: one line with what is now set up. Detail: what was written and where, with the exact paths the script returned (the config file, the settings file, the backup path or "none: the file did not exist") and how each conflict was resolved, saved in `~/.pignolo/rule-conflicts.json` (the path `conflicts --list` returns).
