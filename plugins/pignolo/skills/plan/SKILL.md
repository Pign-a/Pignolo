---
name: plan
description: Entered only through pignolo:entry, when it picked the plan lane (a change that needs a spec). Takes a request from key claims, spec review and an approved scope-card, through a three-step plan audit, to serial execution with a validator per batch and a final review.
---

You are the orchestrator in the main conversation. `<main>` is the project root from the entry skill; `<P>` stands for `${CLAUDE_PLUGIN_ROOT}`; `<plan>` is a slug (`[a-z0-9-]`, at most 40 characters). Talk to the human as the entry skill says: two layers (`<P>/templates/question.md`), a category on every question, ask with `AskUserQuestion`, facts only from script output. Present anything the human must decide with the `pignolo:present` skill.

Every `plan.js`, `plan-audit.js` and `approved.js` call below is `node "<P>/scripts/<script>" … --cwd "<main>"`, even where a step shows it short; every path placeholder goes in double quotes (`--file "<file>"`), because a profile path with spaces splits the argument otherwise.

## Rules that hold in every step

- **Only you write the plan's state.** `plan.js`, `plan-audit.js` and `approved.js` are run by you in the main thread; subagents cannot (the guard blocks them). `next.js` is read-only: run `node "<P>/scripts/next.js" --cwd "<main>"` when you resume and after every step, and follow what it says.
- **Reserved decisions are the human's.** Identity and scope of the product, costs, dependencies, push, publishing, deleting, a contract change, legal matters: ask first, one question per category.
- **Panel.** A question that ends your turn also goes to the panel: `node "<P>/scripts/panel.js" ask --key "plan:<name>" …`, and `panel.js answer` when they reply. Details: `<P>/templates/question.md`.
- **Only the human's approval in their own turn** counts for the scope-card, for a merge and for any reserved decision. A subagent's verdict, your own judgment or an earlier "ok" never does.
- **Models.** Run `node "<P>/scripts/setup.js" models` once and pass `model: <models[role]>` on every dispatch, one `Agent` per mode and per role.
- **Files and messages through Write.** Briefs, reports, claim lists and commit messages go to `<main>/.pignolo/tmp/` with the Write tool; commits use `git commit -F "<file>"`. Stage by path; never `git add -A` or `git add .`.
- **A report is not proof.** Copy each agent's report verbatim into a file and let the scripts parse it. You never drop, merge or reword a finding.
- **Never replay the plan.** The audit reads the plan in place and runs experiments only on the claims; nobody copies the plan into a scratch repository to rebuild it.

## Steps

1. **Open the flow and the record.** `node "<P>/scripts/run.js" start --flow plan --plan <plan> --cwd "<main>"` (exit 1: stop and tell the human what the message says). Write the human's request, word for word, with Write to `<main>/.pignolo/tmp/request-<plan>.txt` and find where this project keeps its specs and plans: `node "<P>/scripts/places.js" where spec --cwd "<main>"` and `node "<P>/scripts/places.js" where plan --cwd "<main>"` (exit 1: stop and tell the human the reason it prints). If `source` is `default`, say once: "no `places` declared: I use the default folder"; if `exists` is `false`, the folder is created when the file is written, and say so. Then run `node "<P>/scripts/plan.js" new --plan <plan> --request-file "<main>/.pignolo/tmp/request-<plan>.txt" --spec <spec folder>/<date>-<plan>-design.md --cwd "<main>"` (the path where step 2 writes the spec; the record keeps it and cannot be changed later). That path, not the map, goes in the brief of every agent and in every task-card.
2. **Brainstorm and spec.** Pignolo does not invent scope: work the design out with the human by these rules, then write the spec at the path given to `new`.
   - **Read before asking:** the request, `project.md`, earlier decisions (`.pignolo/state/decisions/`) and the code the request touches. Then say back what you understood, in one short message with only your reading of the request. An "Ok" to it confirms that reading and nothing else: never an assumption, never a decision.
   - **What the repo answers is never asked:** state it as a fact with `file:line`. A decision found in a past spec, plan or state file is not a fact for a new request: offer it as "previous decision, still valid?".
   - **Classify each open point:** repo fact (state it) · author decision (ask) · technical ruling (decide it, one line with the reason) · measurable (propose an A/B or a spike with its cost; running it is a `costs` question) · researchable (a key claim `K<n>`) · visual (options to look at, offered with their cost when the first one appears) · out of scope (one line). In doubt, it is the author's.
   - **Ask** reserved decisions with `AskUserQuestion` (independent ones in one call, up to 4), recommended option first (`<P>/templates/question.md`). Put low-risk, reversible points in one numbered batch of assumptions, one question with the options "Van así" and "Cambio alguno". A decision is the author's own words in their turn; record each with `node "<P>/scripts/plan.js" decision add --plan <plan> --id D-<n> --text-file "<f>" --quote-file "<f>" --cwd "<main>"` (the quote is theirs, literal).
   - **Budget** of questions: 2 for a small request (one screen or module), 4 medium, 6 large (propose splitting first). Facts and rulings spend none. Put `question <n> of at most <budget>` in the question text and keep `suficiente` as an option of the call.
   - **Stop** when nothing is open, on `suficiente` or when the budget is spent: each open point becomes a declared assumption `S<n>` (what is assumed, why, what changes if false), except an irreversible, cost or security one: that stays a pending question and the scope-card shows it again. For a large author decision, offer a debate of two opus agents (one for, one against) in one line with its cost; never run it unasked.
   - **Spec sections,** in this order before the design: `Pedido` (literal), `Hechos del repo` (with evidence), `Decisiones del autor` (`D-<n>`, date, quote), `Rulings técnicos`, `Supuestos declarados` (`S<n>`, and the pending questions), `Mediciones propuestas`, `Fuera de alcance`.

   Then `node "<P>/scripts/plan.js" advance --plan <plan> --to claims --cwd "<main>"`. Then list the **key claims**: every statement the design leans on about an external system (a platform, an API, the operating system, a tool), each with its system, as JSON `[ { "id": "K1", "text": "...", "system": "..." } ]` written with Write, then `node "<P>/scripts/plan.js" claims set --plan <plan> --file "<that file>" --cwd "<main>"`. If there are none, `claims set --plan <plan> --none-reason "<why>"`.
3. **Review the spec and settle the claims.** Self-review the spec first. Dispatch `pignolo:spec-reviewer` with the literal request, the spec path and the recorded author decisions as a second source (`node "<P>/scripts/plan.js" decision list --plan <plan> --cwd "<main>"`, saved to a file). For each claim dispatch `pignolo:researcher` with an abstract question (no repository, original source mandatory), and always dispatch `pignolo:refuter` on the list itself (the claims and the SHA, not prose). Record each result with `node "<P>/scripts/plan.js" claims resolve --plan <plan> --id <K> --status <corroborated|refuted|inconclusive|hypothesis> --source "<url or reference>" --by <agent> --cwd "<main>"`. A `refuted` claim stays open until the spec stops leaning on it: correct the spec, then close it with `claims resolve --plan <plan> --id <K> --status refuted --superseded --note "<what changed>"` (or run `claims set` again with the new list). Go on only when `node "<P>/scripts/plan.js" claims check --plan <plan> --cwd "<main>"` exits 0. Then `plan.js advance --plan <plan> --to spec-review` (stages only move forward, one at a time).
4. **The scope-card.** `pignolo:spec-reviewer` produces it (its 8 headings are fixed). Save only the card, from `## Goal` to the end of `## Cost estimate` (not the findings, the questions or the verdict word), with `node "<P>/scripts/plan.js" scope-card save --plan <plan> --file "<card.md>" --cwd "<main>"`: a rejection lists the errors, and you send them back to `pignolo:spec-reviewer` to fix; once saved, `plan.js advance --plan <plan> --to scope-card`. Present the card with `pignolo:present` (category `scope-card`), and every reserved decision it detected, one by one. Only the human's approval in their own turn runs `node "<P>/scripts/plan.js" scope-card approve --plan <plan> --quote-file "<file with their words, literally>" [--cap-usd <n>] --cwd "<main>"`. Pass `--cap-usd` per `question.md`. A changed card needs a new approval.
5. **The plan.** Write the plan in the folder `places.js" where plan` gave in step 1: decisions and task-cards (files, interfaces, literal test cases), not final code. Register the tasks (`plan.js tasks set --plan <plan> --file "<json>"`; a task that depends on an item added without being asked names its `A<n>`) and `node "<P>/scripts/plan.js" advance --plan <plan> --to plan-written --plan-file "<path>" --cwd "<main>"`.
6. **Plan audit, three steps** (state lives in `<main>/.pignolo/tmp/plan-audit/<plan>/`):
   1. `node "<P>/scripts/plan-audit.js" check --plan <plan> --plan-file "<path>" --root "<main>" --cwd "<main>"` gives the evidence for step 1 (if it prints `applies: false`, say so in the brief). Its findings are evidence for the reviewer, not a verdict: `finish` counts only what the reviewer keeps in its `findings`.
   2. `plan-audit.js begin-review --plan <plan> --plan-file "<path>"`, then dispatch `pignolo:plan-auditor` in mode `review` (brief: the mode, the plan, the scope-card, the commit and the `check` report). It has no Bash in this mode: a hook denies it. Save its report verbatim and run `plan-audit.js review-done --plan <plan> --report-file "<file>"`. If `begin-review` prints `reaudit: true` (round 2, after a fix pass), dispatch it with `model: sonnet` and a bounded brief: the diff and the round-1 findings it prints, the plan as context; confirm each finding is closed and the change broke nothing else, and do not re-audit what did not change. The fixed probes run as usual; `verify` only for the reviewer's new claims.
   3. `plan-audit.js probes --plan <plan>`: the fixed probes only refute; a claim they do not falsify stays open.
   4. `plan-audit.js begin-verify --plan <plan>` and dispatch `pignolo:plan-auditor` in mode `verify` with the remaining claims and the `scratch` path it prints (skip this if it prints `skipped: true`). A hook sends it back until it ran one experiment per claim. Save its report verbatim.
   5. `plan-audit.js finish --plan <plan> --report-file "<file>"` builds the verdict. `node "<P>/scripts/plan.js" advance --plan <plan> --to audited --plan-file "<path>" --cwd "<main>"` only with `APPROVE` (the record checks the audit against the sha256 of that file). `REQUEST_CHANGES` (round 1 only) goes back to the plan (step 5), then one `begin-review` for round 2; `ESCALATE` goes to the human. With `ESCALATE` and `reason: reaudit-findings`, show the findings with `AskUserQuestion`: "Arreglar y auditar de nuevo" (`end`, start over, with its cost) or "Dejar el plan acá"; the gate is never skipped. `minors` never block: note them at the end of the plan and say so in one line. After a cut, `plan-audit.js end --plan <plan>`.
7. **Before the approval of the scope-card,** run only what `node "<P>/scripts/plan.js" runnable --plan <plan> --profile <profile> --cwd "<main>"` lists (the budget of the profile). That list is the only enforcement of the budget: nothing else stops a task that `runnable` does not list (`scope-gate` only keeps the result away from `main`), so never dispatch one. Once the card is approved: `plan.js advance --plan <plan> --to executing`. Execution is serial until the wave mode exists: create `int/<plan>` from the current branch, and for each task follow the steps of the `pignolo:daily` skill (worktree, test-card, sabotage, `on-done` gate, risk) on the branch `task/<plan>/<NN>-<slug>` from `int/<plan>`; the writers go through `run.js task` with the continuation rules of daily. Merge each task into `int/<plan>` with the human's confirmation (category `irreversible`). Merging `int/<plan>` into the branch it came from is a separate `irreversible` question, and the `scope-gate` hook checks it.
8. **Per batch.** Dispatch `pignolo:validator` (the only place `node "<P>/scripts/holdout.js" run --plan <plan>` is used, with the holdout prepared as in the test-writer flow: the acceptance tests written from the scope-card without seeing the implementation, saved with `holdout.js save`). Then the final review with the `pignolo:review` skill, and the closing summary with `pignolo:present`. After each batch, `panel.js budget` per `question.md`. `plan.js advance` through `validating`, `final-review` and `closed`; `run.js end` at the end.
9. **Approved visuals.** When the human chooses among visual options, save the final version with `node "<P>/scripts/approved.js" save --project "<main>" --flow <flow> --from "<folder>"` and record their words with `approved.js record --project "<main>" --path design/approved/<flow> --quote-file "<file>"`. Then commit both by path in `int/<plan>` before creating the worktree of any task that uses them: `git add design/approved/<flow>/ .pignolo/state/decisions/` and `git commit -F "<message file>"` (the implementer verifies from its worktree, which only has what the branch has). Put the path in the implementer's task-card (`Approved visual`). A change makes a new `-v2` folder; an existing folder is never overwritten.

If the human stops, run `node "<P>/scripts/run.js" end --cwd "<main>"` and say what is left; the branches and the record stay.
