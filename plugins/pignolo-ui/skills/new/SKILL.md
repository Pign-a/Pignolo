# /pignolo-ui:new

Create the screen the user names. The request: $ARGUMENTS

## Values

These are substituted by Claude Code when the skill loads. The support files in `reference/` do not get substitutions, so every command that needs a value takes it from here.

- `<root>` = `${CLAUDE_PLUGIN_ROOT}`
- `<data>` = `${CLAUDE_PLUGIN_DATA}`
- `<N>` = `${user_config.optionsPerDecision}`
- `<profile>` = `${user_config.profile}`
- `<presentation>` = `${user_config.presentation}`
- `<repo>` = the root of the project (the git root of the working directory)

If `<N>` or `<profile>` still starts with `${`, Claude Code did not substitute it (a setting the user never saved arrives like that): use the default from plugin.json (`<N>` is 3, `<profile>` is balanced) and add it to the notices. Never replace `<presentation>` with a default: pass it to `publish-gate` and `present` exactly as it arrived. An unsubstituted `<presentation>` is read by the scripts as local, so nothing is published (D-4c-15).

## Foundation gate

This skill does not work on a project whose product and design are not defined. Right after step 1 and before step 2, read `<repo>/PRODUCT.md` and `<repo>/DESIGN.md`, load `${CLAUDE_PLUGIN_ROOT}/reference/foundation.md` and follow it. If either is missing or undecided, stop and send the user to `/pignolo-ui:define`; go on without it only after the user asked for that explicitly, twice, as that file says, with the pending note in the project's `CLAUDE.md`. An "Ok" is not that request. **A missing or undecided `DESIGN.md` cannot be skipped in this skill, however explicit the request:** end the command and send the user to `/pignolo-ui:define`. Only a missing `PRODUCT.md` can be skipped. Step 2 never starts before this gate is passed or explicitly skipped.

## Steps

1. **Environment.** Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" env`. Keep `pluginVersion` for the first line of the report; do not print it now. If `claude.ok` is false, use the sequential path of `options.md` and add it to the notices. **The notices** of steps 1 to 3 (a default of `<N>` or `<profile>`, `claude.ok` false, no browser, the `line` of `context`) go together in one line of notices, said once before the brief and only if there is any. **Before any call to the Artifact tool, also before `action: "list"`:** `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" publish-gate --data <data> --project <repo> --presentation <presentation>`. With any exit other than 0 (1 is a refusal; 2 is an error, such as a project.json that cannot be read) do not call Artifact at all: use `--artifact no --design-type no` below and work locally (an unreadable `<presentation>`, the literal text that was not substituted, gives exit 1 and the line "ajuste `presentation` ilegible: se trabaja en local"). With exit 0 and the Artifact tool in this session, call it with `action: "list"` and `scope: "types"`: `--design-type yes` only if a listed type has the exact title "Design"; once the run exists (step 2) write its `type_url` to `<run>/types.json` with Write as `{ "design": "<type_url>" }`, never typed by hand. Publishing happens only through `canvas-index.mjs plan` (see `present-and-choose.md`).
2. **DESIGN.md first (only after the foundation gate).** Load `${CLAUDE_PLUGIN_ROOT}/reference/prepare-run.md` with command `new` (create the run and read the configuration and the norms). Load `${CLAUDE_PLUGIN_ROOT}/reference/context.md` and run `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" context --project <repo> --run <run> --values-file <run>/leak-values.json` (its first lines say how to create that file): its `line`, when it is not null, goes to the notices. Then:
   - If `DESIGN.md` exists, validate it with `node "${CLAUDE_PLUGIN_ROOT}/scripts/design-md.mjs" validate ...` and complete what is missing as a diff the user confirms.
   - If it does not exist or is undecided, the gate was not held: stop here and send the user to `/pignolo-ui:define`. Never create or extract one in this skill.
3. **Brief, in chat and in a file.** The chat shows only what the user decides, in at most 12 lines without the questions: (1) one line `Armo: <what it is>`; (2) the screens in order, one line each (the first is the main one); (3) a numbered batch of at most 4 low-risk assumptions, each with its source (`PRODUCT.md`, `DESIGN.md`, the README, screens that already exist) and one question, `¿van así o cambiás alguno?`; (4) the questions that are the user's, at most 3, with AskUserQuestion, recommended first and a free `Otra`. Never ask what the repo already says; what is irreversible, costs money or touches security is a question, not an assumption. `## First look` and `## Do not touch` come from `PRODUCT.md` and are shown only when this screen differs or `PRODUCT.md` lacks them. Everything else (what it is, who uses it, the main action, the inventory of real content, the reading order, sample data) goes to `<run>/brief.md` and is not repeated in the chat: say one line with its path. The user confirms in their own turn. What the user gives is used literally; what is missing is filled with realistic sample values marked `data-sample`, with a visible line "Datos de muestra" on each screen, never real people, emails, companies or brands, invented testimonials or logos, and no brand headlines unless the user gives them (if asked, 2 or 3 proposals, labelled). Keep the literal values the user gave (amounts, dates, names) as a JSON list of strings in `<run>/provided.json`, each value written as it will be shown on screen (amounts and dates are compared by value, whole, not by part). The brief file has two mandatory parts, `## First look` and `## Do not touch` (`nothing` is valid), and `Register:` only if this screen differs from `DESIGN.md` (format in `context.md`): once confirmed, run `context` again with `--brief <run>/brief.md` and paste its `text` into each option brief. `PRODUCT.md` is not created here: that is `/pignolo-ui:define`.
4. **Options.** First decide how they will be shown: step 1 of `${CLAUDE_PLUGIN_ROOT}/reference/present-and-choose.md` (`run.mjs present`, it prints the `destination` that the briefs need). Then load `${CLAUDE_PLUGIN_ROOT}/reference/options.md` and generate `<N>` mockups, each a navigable flow, with the checks it describes (one round plus at most one regeneration).
5. **Choose or combine.** Follow `${CLAUDE_PLUGIN_ROOT}/reference/present-and-choose.md`: the canvas (one per project that grows by a page per run, private, one line of notice and no question) or the local comparison page, the choice from the user's own turn, then the options not chosen leave the canvas and the chosen one is refined there (4c and 4d of that file), and only after the last round `approve.mjs save ... --brief-file <run>/brief.md` and `approve.mjs record` with the confirmed diff.
6. **Implement.** Follow `${CLAUDE_PLUGIN_ROOT}/reference/apply.md`, passing it the path of the approved decision and the list of expected files. With the pignolo core active, its `implementer` receives the same path and list; while its hook denies `pignolo-ui:ui-option`, use the sequential path.
7. **Verify, in `<run>/after/`.** Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/browser.mjs" measure --project <repo> --run <run>/after --url <URL>` (or `--file`), then `capture` and `dom` with the same arguments, at the widths of the mockup, then `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" check --project <repo> --run <run>/after --files <touched files> --base <base>`. Then `compare.mjs approved` (write `<run>/after/map.json` first: `{ "<screen>.html": "<local URL or project path>" }`): `node "${CLAUDE_PLUGIN_ROOT}/scripts/compare.mjs" approved --project <repo> --approved <approved> --map <run>/after/map.json --run <run>/after`. Say its result only when it finds a difference. Copy `<run>/run.json`, `<run>/norms.md`, `<run>/product.md` and `<run>/brief.md` (the ones that exist) into `<run>/after/` with Write and run the auditor on `<run>/after` exactly as `/pignolo-ui:audit` does (`subagent_type: "pignolo-ui:ui-auditor"`, `model: "opus"`, `auditor-check`).
8. **Report.** `run.mjs report-skeleton --project <repo> --run <run>/after --implements <approved>`, then `node "${CLAUDE_PLUGIN_ROOT}/scripts/report-check.mjs" --project <repo> --run <run>/after` and `node "${CLAUDE_PLUGIN_ROOT}/scripts/run.mjs" verdict --project <repo> --run <run>/after --build-ok yes|no`, where `yes|no` is the result of the first `typecheck`, `build` or `lint` script of `package.json` that you ran (`apply.md` step 5); leave `--build-ok` out only when the project declares none. A project that declares one and gets no `--build-ok` is `sin verificar`. Say "terminado" only when the verdict says `terminado`. The first line of the report comes from `run.mjs report-line` and already says the mode, the version and the verdict: the rest of the report does not repeat it in prose.
9. **Next screen.** After the report ask with AskUserQuestion, recommended first: `¿Armamos otra pantalla o componente?`, with "Sí, otra" first when the brief listed screens that are not built yet and "No, terminamos" first otherwise. With a yes, close this report, create a new run (`run.mjs" init`, `prepare-run.md`), reuse `PRODUCT.md`, `DESIGN.md` and the same canvas (the new run adds its page to it), give the new run what `plan` reads (its own `<run>/types.json`, the account types listed again as in step 1, and `<run>/leak-values.json` and `context` as in step 2) and go back to step 3 for what is new. With a no, the canvas stays with the chosen option of each screen.

## Limits (spec section 6)

One round of mockups (plus at most one regeneration), one implementation, one batch check, one batch of fixes and at most one confirmation. When a limit is reached, what is left is reported as pending and the flow ends. The refinement rounds after the choice (step 5) are apart from the one round of mockups and have no fixed cap: the user decides when they are done.

- Options go to a private canvas of the user's claude.ai account when the account has the "Design" type and nothing says otherwise; with `publish: never`, `presentation = local`, "no publiques" or no tool or type they are shown with the local `compare.html` page and nothing is published. The first line of the report says which (`run.mjs report-line` with `canvas`: `published` or `local-fallback` and its `reasons`).
- Exit 1 of a script is a finding; exit 2 is "no verificado" with the reason.
