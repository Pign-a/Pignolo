# Pignolo 2: plan de implementación

> **Para quien ejecute:** usar superpowers:subagent-driven-development (recomendado) o superpowers:executing-plans, o el método liviano del repo (`CLAUDE.md`: un ejecutor en serie, una revisión Opus al final). Los pasos usan casillas `- [ ]`.

**Meta:** reemplazar el plugin actual por un único plugin `pignolo` 1.0.0: cinco skills de usuario más `ui-audit`, seis agentes revisores y la auditoría de interfaz rescatada de pignolo-ui.

**Arquitectura:** el plugin es casi todo markdown (skills y agentes). La única parte con código es `ui-audit`, que conserva las mediciones por script de pignolo-ui aisladas en su propia carpeta. Lo demás (guardia, hooks, registro de tareas, lotes, jueces, panel, publicación al lienzo) se elimina. El plugin anterior queda en la etiqueta `legacy`.

**Tecnología:** Node ≥ 22 sin dependencias npm; pruebas con `node:test` vía `npm test`.

**Diseño:** `docs/specs/2026-10-23-pignolo-2-design.md` (leerlo antes de empezar; manda sobre este plan).

## Restricciones globales (valores del diseño)

- Plugin `pignolo`, versión `1.0.0`, licencia MIT, autor "Ignacio Agustín Miste", repositorio `https://github.com/Pign-a/Pignolo`.
- Carpetas de skills exactas: `start`, `work`, `validate`, `session`, `ui`, `ui-audit`. Ninguna se llama `code-review`.
- Sin hooks (no existe `hooks/` ni `hooks.json`). Nada bloquea.
- Cada `SKILL.md` apunta a unas 600 palabras (§3, principio 4); el detalle va en archivos de apoyo que la skill menciona. Texto interno de skills y agentes en inglés; mensajes al autor en español (`CLAUDE.md` del repo).
- Todo subagente lleva `model` y `effort` explícitos. Los subagentes del plugin no usan `hooks`, `permissionMode` ni `mcpServers` (el plugin los ignora).
- Tope de agentes de `validate`: 5 (decisión del agente, §8). Un diff chico se revisa en el hilo principal.
- Los documentos del usuario nunca se sobrescriben sin mostrar el cambio; ningún archivo escrito por el plugin contiene valores de secretos.
- Commits en español, Conventional Commits, con la línea `Co-Authored-By` que dé el entorno. No se hace push ni se publica sin el OK del autor.
- El repo es público: nada de datos del proyecto donde se usa, personas ni credenciales.

## Foco de revisión (lo que el diseño implica y ninguna tarea prueba de oficio)

1. Proyecto sin git o sin remoto: `session` y `validate` siguen (la base del diff cae al plan B). Lo prueban T4 y T5.
2. Windows no distingue `DESIGN.md` de `design.md`: nunca se crea un segundo archivo. Lo prueba T2.
3. `start` en un repo con `CLAUDE.md` propio: no lo pisa. Lo prueba T2.
4. Proyecto estático sin evidencia de ningún frente: `validate` lanza cero o un agente. Lo prueba T4 y T10.
5. `ui-audit` sin navegador o sin URL local: informa "no verificado", nunca "pasó". Lo prueba T7.

### T4: Skill `validate` y los seis agentes revisores

**Archivos:** `skills/validate/SKILL.md`, `skills/validate/references/fronts.md`, `agents/review-{security,database,code,tests,hygiene,docs}.md`; `tests/validate.test.js`.

**Interfaces que producen:** `validate` imprime siempre una línea `Frentes: <ids>` con ids de `{security, database, code, tests, hygiene, docs}` separados por coma (T10 la compara con lo esperado); la corrección del diff la cubre el `/code-review` nativo, invocado desde el hilo principal.

**`fronts.md`** (tabla de decisión): por frente, la evidencia del repo que lo habilita y qué mira.
- `security`: autenticación, autorización, secretos, datos personales en logs; apoya en `/security-review`.
- `database`: migraciones o esquema (por ejemplo `schema.prisma`, carpeta `migrations`, SQL): reversibilidad, índices, consultas, rendimiento, seguridad por tenant.
- `code`: funciones sin uso, código inútil, duplicados, dependencias sin uso.
- `tests`: tests faltantes y tests tautológicos.
- `hygiene`: capturas de Playwright, trazas, documentos obsoletos, archivos huérfanos. Solo lista; nunca borra.
- `docs`: documentación que ya no refleja el código.

**Agentes:** solo lectura (`tools: Read, Grep, Glob, Bash`), responden con hallazgos y su evidencia sin filtrar por gravedad (la guía de Opus 5 pide reportar todo y filtrar aparte; el hilo principal ordena y descarta). `model`/`effort` por defecto: security sonnet/high (la skill pasa `opus` cuando `security.md` declara datos sensibles), database sonnet/medium, code sonnet/medium, tests sonnet/medium, hygiene haiku/low, docs haiku/low.

**`SKILL.md`** (diseño §5.3): lee `security.md`, el diff y la evidencia; muestra los frentes en una línea con estimación de costo y sigue salvo que el usuario ajuste; un frente solo entra con evidencia; tope de 5 agentes; un diff chico se revisa en el hilo principal sin agentes; se pide con "validá" o en un hito del roadmap, nunca por tarea; la auditoría de interfaz no forma parte (se pide con `ui-audit`); **base del diff**: último commit validado anotado en una línea del registro de sesión, si no el punto de unión con la rama principal, si no los últimos commits (sirve sin git remoto); si falta `security.md`, se apoya en la evidencia y ofrece crear uno mínimo.

**Casos de prueba (`tests/validate.test.js`):**
- existen los seis agentes con los `model`/`effort` de arriba.
- `SKILL.md` contiene `Frentes:`, `5` como tope, `security.md`, `ui-audit` y las tres bases del diff.
- `fronts.md` nombra los seis ids y un archivo de evidencia para `database` (`schema.prisma`).
- ningún agente declara `Write` o `Edit` en `tools`.
- la `description` contiene "validá" y "validate".

- [ ] Prueba, archivos, verificar. Commit: `feat(validate): validación por frentes según la evidencia del proyecto`.
